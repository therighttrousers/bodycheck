## What it is

Tasks that resume only on a tick: work in progress that can be awaited, and `async` methods that return it, run by a scheduler that its owner runs once a tick, and stops when it is done with it. It knows nothing of games, worlds or engines: what a tick is, when it runs, and what clock its waits count are its owner's.

## What it is not for

What runs on it, such as actions, routing or scripts, and when in a tick it runs. Work on other threads, or that resumes whenever something completes: that is .NET's `Task`.

## How it works

- **`TickTask`** is work in progress, which finishes once, fails with an exception, or is cancelled. It has no result yet (`046 §1.5`). An `async` method can return one, through `TickTaskMethodBuilder`. `TickTask.Finished` is one that has already finished, for work that finishes at once.
- **`TickScheduler`** runs them. Its owner gives it a sink for unhandled failures, and one for warnings of what scopes cut short, calls `Run` once a tick, with the tick's length on whatever clock the waits are to count, and `Stop` when it is done with it. Its `Tick` is what its tasks are given.
- **`ITick`** is what a task sees of its scheduler: what to await to let ticks pass. Whatever starts a task passes it the `ITick` to run on, so which scheduler a task belongs to is never hidden state (`046 §1.3`). Every `ITick` is a `ScopedTick`, which makes its waits on its scheduler, so every tick of a scheduler is one scheduler to its tasks, and a chain can await tasks of any of them. Its `Dt` is the length of the tick being run, so that a task can count time on the scheduler's clock (`049 §2.4`).
- **Nothing that awaits a task runs when it finishes.** What comes after each `await` goes to the task's scheduler, and runs when the scheduler next runs, until nothing is left, so that a chain of tasks that finish at once runs to its end in one tick. Finishing a task between ticks only queues what waits for it.
- **An `async` method that returns a `TickTask` awaits only `TickTask`s.** Awaiting anything else would resume it off the tick, so it fails the method's task. The method runs at once up to its first `await` of a task that hasn't finished, and takes that task's scheduler; one scheduler runs all of a chain.
- **Only the scheduler and the method builder make tasks:** the scheduler's waits, and async methods' tasks. Only they finish them (`046 §1.4`).
- **Waiting on conditions.** `ITick.While` loops while a condition holds, checking it once in each of the scheduler's runs, and finishes in the first in which it doesn't. It is the way to wait for what changes in the world, or off the tick, such as the player's input to a menu. Given a body, it runs it each time the condition holds, so that "do this while that" is one call; a body that returns a task is awaited, and the loop waits for the next run only if the body let no time pass. A timeout is a deadline in the condition, from `ITick.Time`, the scheduler's clock (`053 §3.3`).
- **Waiting for what happens off the tick.** `ITick.UntilCompleted` waits for a .NET `Task`, such as one from an engine plugin, and finishes in the first run after it completes, failing or cancelled if the `Task` was. An async method can't await a `Task` itself, since it would resume off the tick, and polling keeps every other thread away from the scheduler (`053 §3.2`). `Task.Delay` is no substitute for `Wait`: it counts real time on a timer, so it runs on through pauses, ignores the game's speed, resumes in whichever tick its thread's timing gives, and outlives a stopped scheduler.
- **Scopes.** `ITick.Scoped` makes a tick whose waits are cancelled once a condition no longer holds, so that what awaits them unwinds as `Stop` unwinds everything: a scope for tasks, such as "while the entity is there", or a timeout, `tick.Scoped(() => tick.Time < deadline)`. The scheduler records each wait with its tick's condition, and checks it when the wait is made, and in each run before deciding whether the wait is due, so a wait isn't finished in the run in which its scope ends. A run settles the waits in the order they were made, and settling one only queues what awaits it, so every condition sees the world as the run found it. A tick scoped from a scoped tick ends with either, and checks the outer condition first, so that it can guard the inner one. A wait whose scope has ended is cancelled with a `ScopeEndedException`, so that the scheduler can tell what a scope cut short from what its stopping did. A scope is only the condition its waits carry: nothing registers, links or disposes it. A condition is called often, so it is cheap and has no side effects. One that throws ends its scope, and its exception goes to the sink, once (`055 §3`). Only what waits on the scope is cancelled: a method suspended on a task of another scope unwinds only once that task settles (`054 §1.4`).
- **Ending cooperatively or preemptively.** `While` and `Scoped` both last while a condition holds, but end differently. `While` checks between steps, and finishes when the condition fails, so that what comes after it goes on: for open-ended work, such as "pull these bodies together while there are any", whose condition failing is its end. `Scoped` cuts a run short partway through a wait, and cancels what awaits it: for work with a goal, such as a door closing, whose scope ending means the goal wasn't met, so that nothing after it acts as if it were (`056 §3.6`).
- **What a scope cuts short is reported.** A task that a scope's ending cancelled, and that nothing has awaited by the end of the run, has cut short whatever it was doing with nothing to hear of it, such as a route's later steps after a script whose scope ended. The scheduler gives its cancellation to the owner's sink for warnings, as it gives unhandled failures to the other, at the top of each chain, so that a beat cut short is never silent. A cancellation from stopping isn't reported, since stopping cuts everything short on purpose (`056 §3.6`).
- **Ending scopes between runs.** `EndScopes` cancels the waits whose scopes have ended, and runs what that unwinds, without a tick passing and without finishing any wait, for an owner that has just ended a scope and must have what runs in it unwind now, while what it cleans up is still there (`056 §3.5`).
- **Stopping.** `Stop` cancels every wait that hasn't finished, then runs what waits, until nothing is left. Awaiting a cancelled task throws an `OperationCanceledException`, so every method waiting on the scheduler unwinds within the call, through its `using` and `finally` blocks, while what they clean up is still there; every suspended method waits, down its chain, on one of the scheduler's waits, so none is missed. A wait made after it has stopped, such as by a `finally` block, is cancelled at once, and it runs no more ticks. A cleanup that throws fails its method's task, as any failure does, so it goes to the sink if nothing awaits it, once everything has unwound (`053 §1.1`, `§2.1`, `§2.2`, `055 §1.6`).
- **Cancelled isn't failed.** A cancelled task is never unhandled, and an async method that throws an `OperationCanceledException`, such as from awaiting a cancelled task, is cancelled, not failed, so that cancelling a chain isn't reported as a failure on the way up. One whose cleanup throws something else fails as usual. Only the scheduler cancels tasks, when it stops or a scope ends: there is no cancelling a single run on request. A run that should end early either ends itself, cooperatively, or runs on a scope that ends (`053 §1.2`, `§1.3`, `§4.1`, `054 §1.4`).
- **Catching everything catches cancelling.** A method that catches every exception catches a cancellation too, against the root's conventions, and runs on until its next `await` throws again (`053 §1.4`).
- **Waiting.** `ITick.Wait` finishes once that much time has passed on the scheduler's clock, which counts the ticks it runs from the end of the last one: in the run whose tick ends nearest, so that rounding never adds a tick, but never in the run it is made in, so that a loop that waits can't spin within a tick. `NextTick` waits for no time, so it finishes in the scheduler's next run: for a task the scheduler resumed, the next tick's; for a wait made before this tick's run, this tick's.
- **Failures go to what awaits them, or to the sink.** A failed task throws its exception in what awaits it, as `await` does with any exception, so a failure unwinds its chain through its `using` and `finally` blocks. A task that failed in a run and that nothing has awaited by the end of the run is unhandled: the scheduler gives its exception to the sink its owner gave it, in the order failed, so that it is never lost. Each chain is reported once, at its top, and everything else carries on in the same run. `Run` and `Stop` don't throw a task's failure; a sink that throws throws from them. An async method that fails before its first `await` has no scheduler, and throws to its caller, as a method that isn't async would (`055 §1`).
- **Waiting for several.** `ITick.All` finishes when every one of its tasks has. It enumerates them before awaiting any, so that a sequence that starts them as it goes, such as a `Select` of calls, starts them all at once. There is no `Any`, finishing when the first does: the others would run on, and a race used for a timeout would leave the loser acting on the world, so it waited for a way to cancel them (`053 §3.3`). Scopes are that way, but there is no `Any` yet.
- **Re-entry.** A `ReentrantTask` starts runs of work that may be asked for while one is in progress, as its `Reentry` says, so that what responds to requests says in one line what a second one does. Each request passes what starts a run, which the policy calls or not: `Join` gives a request made during a run that run, and starts nothing; `Once` starts only the first run, and gives that run to every request, so that one made after it finishes at once; and `Queue` starts a run once the last one asked for has finished, so that runs follow one another in the order asked. A run that was cancelled has ended, so a request after it starts a run of its own. Work that runs every request alongside any in progress needs none: it just starts a run. One `ReentrantTask` may serve several kinds of request, such as two actions, which then count as runs of the same work, so that with `Join` one gets the other's run (`043 §1.10`, `047 §2.1`). A request made while a run is being started, up to its first wait, throws, under every policy and whether or not another run is in progress: no policy can serve it, and with `Queue` it would deadlock, waiting for the run that waits for it, but only when another run was in progress. So work that shares a `ReentrantTask` calls the work itself, not the requests that go through it: a door's toggle starts the work of opening, not a request to `Open` (`049 §3.1`).
- Tasks and their scheduler are for one thread.

## Open questions

- Ignore, a re-entry policy which finishes at once while a run is in progress, when something needs it (`043 §1.10`).
- Cancelling everything without stopping the scheduler, such as to start an important cutscene: what was left half done, such as a door unfrozen partway through closing unless its `finally` freezes it, and whether waits made while unwinding are cancelled (`053 §4.2`).
