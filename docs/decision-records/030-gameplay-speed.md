# 030: Gameplay speed

## Context

Inciting event (2026-10-26): Neil watched a gameplay video from the day before, and the game looked very fast. He asked how the game's speed could be tuned while leaving most of the rest as it is.

The game has been slowed once already, by hand: speeds were multiplied by 0.75 and accelerations by 0.75². Most movement comes from forces and impulses, so the same could be done automatically, with a `Features.GameplaySpeed`. But not everything should scale. The half-second slowdown to the phase pause and the phase cooldowns should stay the same, while the spawn cooldown should grow as the game slows.

Goals:
- One feature that sets how fast the game plays, with the tunings, tests and telemetry kept at speed 1.
- What is about the player's hands stays the same at any speed.

Anti-goals: choosing the speed. That is for playtesting.

## 1. Mechanism

- [x] 1.1 How does the speed reach what moves? Options:
  - (a) Scale every value by the power of time in its units: speeds, impulses and rates (including drag, `PlatformDriveGain`, `PlatformHoldFrequency` and `Entity.LevelingRate`) by `s`, forces and accelerations (including gravity) by `s²`, and durations tied to motion by `1/s`. Gravity is a project setting that `Constants.Gravity` reads once, so it would have to be pushed into the physics server. Jump thrust is a whole number of ticks, which `1/s` breaks. Values outside `Features` would each need a `× s` where they are used, which is easy to miss (Claude).
  - (b) Set `Engine.TimeScale` from the feature. At a fixed tick rate, scaling speeds by `s` and accelerations by `s²` integrates step for step the same as scaling each tick's `dt` by `s`, so (b) is (a) done everywhere at once, including gravity, drag and thrust (Claude).
  - Decision (Neil): (b). `Features.GameplaySpeed` sets the engine's time scale outside the slowdown and the pause. What must not scale runs on real time, which `018 §1` already separates from game time.
- [x] 1.2 How does the slowdown to the phase pause combine with the speed? Now a tween sets `Engine.TimeScale` directly, falling in a straight line from 1 to `SlowestTimeScale` (0.05) over half a real second, and `Muffler` works out how far it has got from the time scale. Options:
  - (a) Multiply: the time scale is `GameplaySpeed` times a slowdown factor that falls from 1 to 0.05. What happens during the slowdown is then the slowdown at speed 1, scaled in time like the rest of the game. The floor becomes 0.05 × `GameplaySpeed`, smaller at slow speeds.
  - (b) Fall in a straight line from `GameplaySpeed` to an absolute 0.05. The floor stays where it is, but the slowdown's shape changes with the speed, so a slower game slows down to the pause differently.
  - Under (a), where the factor lives: (a1) the tween animates a factor that `GameModeManager` holds, and sets the time scale from it and the feature, and `Muffler` reads the factor; (a2) the tween still sets the time scale, and `Muffler` divides `GameplaySpeed` out.
  - Claude leaned (a1). (a) keeps a slower game a slower copy of the same game, including the slowdown, and (a1) gives `Muffler` the slowdown's progress, which is what it wants, without working it back out of engine state. The factor is the slowdown's own state, not a second copy of the engine's.
  - The floor of 0.05 was chosen because it is below where Neil noticed a pop going from the slowdown to the pause. Multiplying only lowers it, since the speed won't be raised above 1, and the speed almost certainly won't go below 0.5. A tick of 0.025/60 game seconds is probably not a problem (Neil, Claude).
  - Decision (Neil): (a1), multiplying for simplicity.
- [x] 1.3 What sets the time scale, and when? `GameModeManager` owns it now, in the game project, and resets it to 1 on each change of mode. With §1.2's (a1), it holds the slowdown's factor too. Options:
  - (a) Each physics tick, `GameModeManager` sets `Engine.TimeScale` to the factor times `Features.Current.GameplaySpeed`. The tween changes only the factor, and a change of mode resets the factor to 1, not the time scale. The time scale is set in one place, and nothing subscribes to `Features.Changed`, so nothing can keep the node alive. It steps after the world, so a change to the speed takes effect at the next tick, within `016 §3.1`'s bound, like a copy into the engine under `029 §2.2`. It goes on setting it while the tree is paused, which is harmless.
  - (b) Set it when the factor changes, in the tween's method and on a change of mode, and when the features change, by listening to `Features.Changed` while in the tree, as `WorldNode` does (`029 §2.5`). Less work per tick, but three places set the time scale instead of one.
  - Claude leaned (a): one multiplication and an assignment per tick costs nothing, and the time scale has one source.
  - Decision (Neil): (a).

## 2. Which clock

- [x] 2.1 The slowdown to the phase pause runs on real time already, through a tween that ignores the time scale (`018`), so it stays half a real second at any speed.
- [x] 2.2 The spawn cooldown stays on game time: it is there so that spawning again and again can't be flight, which depends on how fast the player falls. At a speed of 0.75 it lasts 2 real seconds. The spawn-cancel cooldown and the platform's stall time stay on game time too, and so does jump thrust, since otherwise the jump's height would change with the speed.
- [~] 2.3 The phase cooldowns (`PlayerPhaseThrowCooldownTime`, `PlayerPhaseCancelCooldownTime`) should stay the same at any speed (Neil), so they move to real time. That reclassifies them under `018 §1.1`: they are about the player's rhythm, not the world's. The slowdown doesn't overlap them, since a phase can't begin until its cooldown is over (Claude). To be confirmed.
  - Under §2.6's rule, on real time they would be given in ticks, and neither is a whole number of ticks now: 0.125 s is 7.5 ticks, and 0.25 s is 15 (Claude). That prompted a second look (Neil).
  - Decision (Neil): `PlayerPhaseCancelCooldownTime` stays on game time. It is there to keep the player from hovering by phasing near something again and again, which depends on how fast the player falls, as the spawn cooldown's purpose does (§2.2).
  - `PlayerPhaseThrowCooldownTime`: Neil now leans towards game time too. To be checked by playing.
- [x] 2.4 Coyote time runs on game time, so as the game slows it lasts longer in real time while covering the same distance past the edge. Neil leans towards real time: at half speed, coyote time would look awfully long. During the slowdown, coyote time running out in real time is harmless, since the player's gravity scale is 0 and the player can't jump then (Neil). Against it: on real time, the distance past the edge that still allows a jump shrinks as the game slows (Claude). Leaning real time; to be checked by playing.
  - On game time, coyote time would look the same at any speed: the player gets just as far past the edge, and falls just as far. What changes is how lenient it feels, since the player gets more real time to react. Coyote time is there for the lag between seeing the edge go and pressing jump, which is in the player, as the jump buffer's is. So `018 §1.1`'s rule puts it on real time, beside the jump buffer, whatever it looks like (Claude).
  - On real time, nothing else changes: the paused step doesn't count it down, the tree doesn't tick while paused for the menu or the map, and the grounded animation, which reads it, lasts the same few real ticks (Claude).
  - Decision (Neil): real time.
- [x] 2.5 Jump buffer and phase release leniency run on real time already (`018 §1.1`), so they don't change.
- [x] 2.6 Durations are tuned in ticks at 60 per second, converted by `Features.TicksToTime` to half a tick short of a whole number (`018 §2.1`). At a speed other than 1, a duration in game ticks no longer lasts a whole number of real ticks, so tuning in ticks stops making sense (Neil). Options:
  - (a) Tune durations in seconds, and replace `TicksToTime` with something that rounds a time to half a tick short of the nearest whole number of ticks, under a new name.
  - (b) Tune durations in seconds, and drop the rounding, if it isn't worth the bother once durations aren't given in ticks (Neil).
  - Real-time durations still count down by exactly one tick's length each tick, so for them the rounding still guarantees a whole number of ticks. That covers jump buffer, phase release leniency, and coyote time if it moves to real time (§2.4). Only game-time durations, such as jump thrust, lose it (Claude).
  - Neil, after §2.4: real-time durations should still be given in ticks, so `TuningTicksPerSecond` and `TicksToTime` stay. What doesn't make sense is giving game-time durations in ticks, since a tick's length in game time changes with the speed.
  - But one game-time duration is still given in ticks: `PlayerJumpThrustTicks`, which counts down by game time, and stays on game time (§2.2) (Claude). Options for it:
    - (c) `PlayerJumpThrustTime`, in game seconds, counted down as now. At a given speed every tick has the same length, so every jump still thrusts for the same number of ticks. But a time that is a whole number of ticks at that speed could land either side of zero when summed in floats, which is what `018 §2.1` guards against.
    - (d) Keep it in ticks at speed 1, converted to game time with `TicksToTime` as now. At speed 1 it lasts exactly that many ticks. At other speeds it lasts whatever the game time comes to, which is the time scaling the rest of the game gets.
  - Under either, at some speeds the duration is a whole number of game ticks: under (d), 14.5 ticks at speed 1 is exactly 29 at speed 0.5. Summing in floats could then land either side of zero. But at a fixed speed every tick's game time is the same, so the sum comes out the same on every jump: the count is consistent, only not predictable on paper. That is the consistency `018 §2.1` was after, at the cost of up to a tick of thrust (Claude).
  - Claude leaned (d): nothing changes, and a feature tuned at speed 1 stays meaningful at any speed, as the forces and speeds do. (c) and (d) give the same game duration, and so the same jump: they differ only in the unit the feature is given in.
  - Decision (Neil): (c), for uniformity, so that a duration's unit tells its clock. A rule: game-time durations are given as times, in game seconds, and real-time durations in ticks at `TuningTicksPerSecond`, converted by `TicksToTime`. `PlayerJumpThrustTicks` becomes `PlayerJumpThrustTime`.

## 3. Consequences

- [x] 3.1 The camera and the animations use the scaled process delta, so they speed up and slow down with the game. That is probably right for the animations; check `CameraRig`. Open.
  - `CameraRig`, checked (Claude). It processes always, even while the tree is paused, and three things in it run on the scaled delta:
    - Phantom Camera's follow damping. Scaled, the camera lags the player by the same distance at any speed, as it would in a slower copy of the game. Right as it is.
    - The look up or down: a delay of half a second, then a pan of a second, by a tween on game time. Holding up or down is the player's hands, so by `018 §1.1` it would run on real time, with `SetIgnoreTimeScale`, as the slowdown's tween does.
    - Phantom Camera's tween to the map camera and back, 0.25 s. The tree is paused in the map, but by §1.3 the time scale is still `GameplaySpeed` there, so at speed 0.5 the move to the map takes half a real second. Until now the time scale was always 1 in the map.
  - The last raises a wider question: what should the time scale be while the tree is paused, in the menu, the map or the phase's pause? Only what processes always runs then, and none of it is the world, so the gameplay speed means nothing to gameplay there. Options:
    - (a) `GameplaySpeed` always, as §1.3 has it. The map's camera moves at the game's speed.
    - (b) 1 while the tree is paused. The move to the map runs at 1, but the move back runs mostly after the tree is unpaused, at the game's speed.
    - (c) As (a), and what must run in real time ignores the time scale itself, as the look's tween would. Phantom Camera's tween is in the addon, so it may not be ours to change.
  - Claude leaned (a), with the look on real time: the map's move isn't gameplay, but a slower one is harmless, and (b) brings back a special case.
  - Decision (Neil): (a), with the look on real time. The move to the map and back must stay quick when the game is slowed, so it runs in real time too, just as aiming a phase does: by dividing its tween's duration by `GameplaySpeed`, for example, or by some other means of running it in real time. The time scale is `GameplaySpeed` in the map, since a change of mode puts the slowdown's factor back to 1 (§1.3).
- [x] 3.2 Speeds above 1 move bodies further each tick, which tests continuous detection against walls (`028`) harder. Is there a range for the feature? Neil (§1.2): the speed won't be raised above 1, and almost certainly won't go below 0.5. Leaning towards that range; whether it is enforced is open.
  - No feature's range is checked now, and ranges were left to the developer menu's metadata (`016` anti-goals). So the range would go in the feature's doc comment, unchecked, like the others' (Claude).
  - Decision (Neil): from 0.5 to 1, stated in the doc comment and not checked.
- [x] 3.3 Tests run at a time scale of 1 unless they set the feature, and whatever applies it lives in the game project. Do tests need to cover a speed other than 1, for the clocks in §2? Open.
  - The tests reference the game project, and `PhaseTest` already makes a `GameModeManager` and puts the time scale back to 1 after each test, so a speed can be tested where it is applied (Claude). Candidates, kept few:
    - The time scale is `GameplaySpeed` while playing, and falls from it during the slowdown (§1.2, §1.3).
    - At speed 0.5, coyote time lasts the same number of real ticks as at speed 1 (§2.4), and the jump at full thrust rises as high as at speed 1, give or take a tick of thrust (§2.2, §2.6).
  - The tests that count `PlayerJumpThrustTicks` change with it, to `PlayerJumpThrustTime`.
  - Decision (Neil): those two, and the change to the thrust tests.
  - What if the default `GameplaySpeed` is lowered? Tests that count ticks would fail, unless their fixtures set the speed to 1 (Neil). But only `GameModeManager` applies the speed, and only `PhaseTest`'s test of the slowdown to the pause makes one; every other test runs at a time scale of 1 whatever the feature is. That test waits for the pause for up to 120 ticks, and the slowdown takes 30 real ticks at any speed. So lowering the default breaks no test now. The speed tests above set the speed they test (Claude).

## 4. Results

- [x] 4.1 Built, 2026-10-26 (Claude). `Features.GameplaySpeed`, 1 by default. `GameModeManager.SlowdownFactor`, with `SlowestTimeScale` renamed `SlowestSlowdownFactor`, since it is the factor's floor now. `Muffler` reads the factor. Coyote time counts down by real time. `PlayerJumpThrustTime` is 0.225 game seconds, 13.5 ticks' length at speed 1, so that thrust lasts 14 ticks there, as 14 ticks did, with half a tick to spare; the example configuration's 18 ticks became 0.29. The look's tween ignores the time scale, and the rig sets both phantom cameras' tween durations to 0.25 / `GameplaySpeed` on each change of mode. 141 of 141 tests pass, among them the new `TheTimeScaleIsTheGameplaySpeedAndTheSlowdownFallsFromIt`, `The_tallest_jump_at_half_speed_rises_as_high_as_at_full_speed`, and the coyote test at time scales of 1 and 0.5.
- [x] 4.2 Played, 2026-10-26 (Neil). The muffling follows the slowdown. Jumps keep their shape: the highest rises about 4.57 tiles, as before, such as 4.54 at a speed of 0.85.
- [x] 4.3 Fixed by Neil: the map move's duration must be multiplied by the speed, not divided, since the host counts it in game time, which runs slower. And looking up or down didn't feel the same at a lower speed until the follow damping was scaled too. Phantom Camera's damping value is a smoothing time in seconds, about how long the camera takes to catch up, used only through `delta`, which is game time; checked in the addon's `_smooth_damp` (Claude). So the rig multiplies it by the speed each frame, which keeps it the same in real time. The map camera follows nothing, so its damping has no effect, and isn't set.
- [x] 4.4 Scaling the follow damping trades one sameness for another. Unscaled, the camera lags a player moving steadily by the same number of tiles at any speed, as a slower copy of the game would; scaled, it follows a look and snaps back from it as quickly at any speed, but lags a moving player less as the game slows (Claude). Neil will try it unscaled.
  - Tried (Neil): scaled, on real time, only while the player looks up or down, and on game time otherwise. Then the snap-back from a look runs on game time, which is slow at a speed of 0.125, though hard to notice at 0.85 (Claude, Neil).
  - Decision (Neil): game time throughout, unscaled. The difference while looking is too small at reasonable speeds to be worth it. Its smoothing time is now 0.15 seconds.
- [x] 4.5 Fractional thrust (Neil, after 4.2). Thrust was applied on every tick that started within its time, so how much of it a jump got depended on where the ticks fell: at speed 0.85, 0.225 seconds gave 16 ticks of 0.85/60, about 0.227 seconds, against 0.233 at speed 1, and the highest jump rose 4.54 tiles, not 4.57. Now the last tick gets only the share of the thrust that the time left covers, so the thrust's impulse is the same at any tick length, and there is no edge for floats to land on. `PlayerJumpThrustTime` is 14 ticks' length at speed 1, 0.2333333, so that the jump is as it was there; the example configuration's became 0.3, its 18 ticks. Measured at speed 1, 4.5726 tiles; at speed 0.5, 4.6500, the rest of the difference being the engine's integration, which rises a little higher with shorter steps (Claude).
- [x] 4.6 Retuned (Neil), at speeds 1 and 0.85. At speed 1, `PlayerJumpThrustTime` is 0.23 seconds and `PlayerJumpThrustFrac` 0.885, and the jumps rise 2.50 and 4.50 tiles; at speed 0.5 the highest rises 4.58. `slower-gameplay.jsonc` tunes the jump speed and the thrust's fraction for 2.5 and 4.5 at speed 0.85, leaving the thrust's time alone, since how long jump can be held is an affordance. The example configuration `strong-jump.jsonc` is gone. The thrust tests now reckon with the thrust's time, which ends partway through a tick (Claude).
