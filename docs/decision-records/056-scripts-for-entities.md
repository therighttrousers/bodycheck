# 056: Scripts for entities

## Context

Inciting event (2026-11-07): Neil wants scripts that start when an entity spawns and know which entity they are about, such as a script that makes robots do things when they spawn, which has to know which robot. The test case is a block that hovers and follows the player around. `RunRightOffLedge` drives only the player, in a cutscene, and should stay that way. `IScriptWorld` has just gained `Tick`, so that `IScript.Run` takes one argument.

Goals:
- A script can start when the world does, with no player action to set it off.
- A script knows the entities it is about, checked when the world is built, as its class name is (`051 §2.3`).
- A script about an entity ends when the entity is removed, through its `using` and `finally` blocks, while the entity is still whole.
- No level field that a later design would have to replace. Changing what levels hold means fields that coexist until the levels are converted, or a converter that Neil, and the playtester when he merges `main`, has to run.

Anti-goals:
- Arguments checked only when a script reads them, such as names or strings looked up at run time.
- A script that drives a body directly, beside the controller that drives it.
- Cancelling single runs on request, which `053 §4.1` decided against.

Tensions: entity-scoped runs are a way of cancelling single runs, which `053 §4.1` left out, though here the cause is an entity's lifetime rather than a request. Scoping ticks to entities risks mirroring the scene's tree in the scheduler, which Neil wants to avoid if a flat design does as well.

The items on scoping runs, 3.1, 3.2, 3.9 and 3.10, were moved to their own record, `054`, so that the scheduler's work could land on its own; their numbers here are kept, so that the other items' references hold.

## 1. Starting scripts

- [x] 1.1 How a script starts when the world does. Options:
  - (a) `TriggerSetOffBy.Start`: a trigger set off once, when the world starts. Uniform: anything a trigger can run can start with the world, such as a `Sequence` at the start of a level, not only scripts.
  - (b) A field on each kind of entity that can have a script, such as `ClassName` on `Block`, which `WorldNode.CreateBlock` runs. Ties the script to the entity's lifetime directly, but every kind that wants one needs the field, and it goes around the routing. It is a controller chosen by name, in another form: if per-entity behaviour is to be chosen in LDtk, a field that names a controller class is the uniform version.
  - (c) `Target` and `Action` on `Block`, so that a body sets off a route, with a `Caller` given to `IScript.Run`. Makes every body a source of routes, for one case, and what the caller is gets unclear through a `Sequence`: the `Sequence`, or what set it off.
  - Decision (Neil): (a), built as `TriggerSetOffBy.Start`.
- [x] 1.2 When in the tick a `Start` trigger is set off: in the first played tick, with the triggers set off by touch (`048 §1.4`), so that what it starts runs on in that tick's run, as with any trigger. Built so (Claude). One that is off in that tick and turned on later: does it fire then? Decision (Neil): no, for now: it is set off only in the first played tick, if it is on then. Whether a world rebuilt after the game state loads counts as starting again, and so whether `Once` matters for it, waits for the game state.
- [x] 1.3 The first tick, which §1.2 sets `Start` triggers off in. The engine steps the world after each physics tick, so in a world's first, no body has contacts and no area holds anything. A world built during a physics tick, as on a reload, may be stepped before its first; one built before the game's first physics tick isn't. Found when `RunRightOffLedge`, set off at the start, saw the player off the ground and stood still on the game's first world only. Decision (Claude, at Neil's report): a world sets triggers off and runs its scheduler from its second physics tick, so that every world starts the same way, with one step taken, and a script sees what the engine has found. `Start` triggers are set off in that tick.
- [x] 1.4 A `Start` trigger that starts off. Under §1.2 it is never set off, and turning it on doesn't change that, so it is either a mistake or a way to disable a trigger that wiring can undo at runtime, which is the wrong way. Decision (Neil): the world rejects it when it is read.

## 2. What a script is given

- [x] 2.1 Where a script's arguments are given. Options: on the `Script`, which says what it is about in the level, where the reader can check it; or on what sets it off, a trigger, which is better at saying *who* set it off (an instigator, such as a block on a pressure plate, `043 §4.3`) than *what* to act on. Claude: on the `Script`, and the instigator kept apart, if something needs it. Decision (Neil): on the `Script`, whose `Entities` field he added.
- [x] 2.2 The shape of the arguments. LDtk fields are defined per entity definition, not per instance, so one `Script` definition can carry only a fixed set of fields, each a value or an array of one type. Options:
  - (a) A single `Target`, an entity reference. Enough for the test case, but a later need for other arguments puts it beside them for good, or replaces it with a conversion (Context).
  - (b) One array field per useful type: `Entities` (entity references) now, and `Numbers`, `Points` or `Strings` when a script needs them. The script declares its parameters, and each takes the next element of its type's array, in order. Every later step adds a field, so nothing is replaced. Binding by position is the weak spot: two parameters of the same type can be swapped with no check catching it, and LDtk shows `Entities[0]`, not a name. It is the trade accepted for `Sequence`'s `Targets` and `Actions` (`043 §1.5`), and a script with more than about three arguments is probably doing too much.
  - (c) An LDtk entity definition per script that takes arguments, such as `HoverFollow`, whose fields are named and typed in LDtk, with LDtk's own pickers. The reader matches field names to the script's parameter names. Costs a definition in the LDtk project for each such script. It can be added beside (b) later, as an upgrade, with nothing replaced.
  - (d) A string of named values, such as JSON. Named, but loses LDtk's entity picker, and is checked by nothing until the reader parses it.
  - Leaning (Claude, Neil wary of (a)): (b), with `Entities` only, and (c) if positions turn out confusing. The reader treats a field missing from an older level's JSON as empty.
  - Decision (Neil): (b), with `Entities` only: an array of entity references, which LDtk restricts to the tags `Character` and `Prop`. LDtk saved the field into every `Script` when it was added, so the reader requires it, as it requires every field, rather than treating a missing one as empty. `World` checks that each is in the world and has a body.
- [x] 2.3 How a script declares its parameters. Claude: as a primary constructor, such as `HoverFollow(HoverController block, Entity leader, float height)`, which the script library calls with the arguments. A new instance is still made for each run (`043 §5.1`), but no longer with a constructor of no arguments. `WorldNode.Build` reflects over the script's one public constructor and checks that each array has as many elements as there are parameters of its type, and that each entity, or its controller, has the parameter's type, as it checks the class name now (`051 §2.3`). The class of a block is `Entity`, so a parameter typed by entity class can't tell a block from other plain entities; typing it by controller can.
  - Built so (Claude), with Neil's test case of any number of bodies (§4.2): a last parameter of `IReadOnlyList` of a type of `Entity` takes the rest. The rules are in `Scripts.ScriptArguments`, which the game's library uses, so that they are Core's, not each library's. A script needs one public constructor. Since `Build` checks before it has entities, it asks the library about the entities' classes, which `WorldNode.EntityClassOf` gives for each kind, asserted against what it builds.
- [x] 2.4 What a script drives. Behaviour is a controller's (`043 §2.1`, `§1.9`), and `RunRightOffLedge` drives the player as a player would, through `PlayerController.ScriptedInput`, so the controller keeps the physics (`051 §3.3`). Claude: the same for every entity: a script sets its target controller's goals, such as a point to hover towards, and never pushes the body. A parameter typed by controller (§2.3) gives a script exactly that. It also means the hovering block needs a controller, which blocks don't have yet, whatever else is decided.
  - Decision (Neil): as Claude put it, and as §4.2 found: a script drives a body that has a controller through the controller, and may push one that has none. A script may also do what no controller does, such as lifting the player into the air with a melody playing after a powerup is found; it does so in a cutscene, which keeps the controller and the script from fighting.
- [x] 2.5 What an entity's script sees of the world. `IScriptWorld` holds the player's controller and `HoldCutscene`, for scripts like `RunRightOffLedge`. A script about a robot needs neither. Options: the same `IScriptWorld` for every script; or a narrower view for scripts about entities, such as `IWorldView`, their tick, and their arguments, with `IScriptWorld` extending it for the cutscene scripts.
  - Decision (Neil): the same for every script, and it sees everything. A narrower view would be widened request by request until scripts see essentially the whole world anyway.

## 3. Scoping a run to an entity

- [x] 3.1 Moved to `054 §1.1`.
- [x] 3.2 Moved to `054 §1.2`.
- [x] 3.3 What a script that mixes ticks gets. A method suspended on one tick's wait is cancelled only when that tick is stopped. So a script about an entity that awaits the world's tick, such as `world.Tick.Wait(2)`, isn't cancelled when its entity is removed: it unwinds at its next await on the entity's tick, and one that loops on the world's tick forever runs on, acting on an entity that is gone. This holds under every option of `054 §1.2`. Claude, first: a script about an entity is given only its entity's tick, as its world's `Tick` (§2.5), so that it can't await the world's by mistake. Neil: a script may be about several entities (§3.8), so there is no one entity's tick to give it.
  - Settled by `054`: a script isn't given an entity's tick. It makes its own scope from its world's `Tick`, with a condition such as its entities being live, and a wait on that scope is cancelled when the condition stops holding. A script that waits on its world's `Tick` instead has chosen not to be scoped for that wait, and is not cancelled; nothing to mix by mistake.
- [x] 3.4 Whose tick a controller's async action runs on. Today whatever starts a task passes the tick it runs on (`046 §1.3`). If a door's `Close` is to end when the door is removed, the door runs it on its own tick, whoever asks. Claude: a run belongs to what runs it, so the controller's own tick, which reverses `046 §1.3` for actions.
  - Decision (Neil): a controller's action runs on a tick scoped to its entity's lifetime, such as an entity's own `Tick`, made lazily from its world's. This isn't at odds with scripts making their own scopes (§3.8): a controller means nothing without its entity, so it never outlives it, whereas a script's lifetime is its own to choose.
- [x] 3.5 When an entity is removed. `Entity.StopAndQueueFree`, mirroring `WorldNode.StopAndQueueFree` (`053 §2.3`), stops its tick, so that its runs unwind while it is still in the tree, and then queues it to be freed. A tick can't be stopped while it runs, and an entity may be removed by a controller or a script partway through the tick, even by the script it is running. Claude: the call only marks the entity, and the world removes it at a fixed point in its tick, as `IDefer` defers actions, while the world's scheduler runs, so that the unwinding is part of the tick's run.
  - Claude's sketch, in full. `Entity.Remove()` only marks the entity, and may be called from anywhere, any number of times. `IsLive` is false from then on, so a scope whose condition is its entities being live ends at once. At the end of the world's played tick, after its scheduler's run, the world:
    1. Asks the scheduler to settle its scopes: every wait whose condition no longer holds is cancelled, and what that cancels runs, as in a run but without time passing or due waits finishing. The removed entities are still whole and in the tree, so `finally` and `using` blocks can act on them. This may remove more entities; they are taken in the same pass.
    2. Takes the removed entities out of everything that holds them: its list of entities, which keeps each entity's configuration beside it, so that `EntitiesOf` no longer pairs by index; and other entities' joints to them, through a hook each entity overrides, as the walker's grip and the carried body's steadying.
    3. Frees them with `QueueFree`. `Support` and `Above` are rebuilt from contacts in the next step, so they never see a freed entity after it.
  - The player can't be removed: `Remove` on it throws, since the camera, the controller the game reads and `IScriptWorld.Player` all assume one. Dying is respawning, for now.
  - A route whose target is a removed entity's controller: its action finishes at once, as a `Respawn`'s does when it can't act yet, and is logged as a warning, so that wiring doesn't hang and isn't silent.
  - Removal in a paused tick, such as by the phase: none can happen there yet, so the world asserts that nothing is marked when it steps paused.
  - For §3.4: rather than an entity's own `Tick` made from its world's, a controller scopes the tick its action is given, `tick.Scoped(entity.IsLive)`, so that the action ends with the caller's scope or with the entity, whichever ends first.
  - Decision (Neil): the sketch, with these changes, as built (Claude):
    - Removal goes through the world, `IWorldView.Remove(entity)`, rather than `Entity.Remove()`, since the world is what refuses the player and the player's block. It always refuses them: `WorldNode.Player` and `IWorldView.PlayerBlock` would otherwise yield defunct entities (Neil).
    - `IsLive` is false as soon as removal is asked. That makes a little order-dependence within the tick, which Neil accepts.
    - An entity queued to be freed is still in the engine until the end of the frame, so it would collide in the step after the tick, and a sleeping body under it, whose `_IntegrateForces` doesn't run, would keep it in `Above`. So the world takes it out of the tree at once, and every other entity forgets it, as what it stands on, what is above it, or what a motor is anchored to, and is woken if it remembered it.
    - A route to a removed entity's controller isn't a case of its own: with §3.4, the controller's action is scoped to its entity, so its first wait is cancelled at once, whoever runs it, a route or a script holding the controller; the cancellation propagates, and §3.6's warning reports it. Controllers needn't check `IsLive` themselves: the world no longer steps a removed entity, and touching a freed body throws.
    - The paused path takes removed entities out too, at the end of `StepPaused`, rather than asserting that none are removed there.
- [x] 3.6 What awaits a run cancelled by its entity's removal, such as a `Sequence` whose step was a script about the entity. Today a cancellation propagates up: the `Sequence` is cancelled too. Options: as today; or the awaiter sees the run as finished, and goes on, which needs a way to tell a scope's cancellation from the world's. Claude leans to going on: the removal is the entity's, and wiring shouldn't come apart because a robot is gone. Neil leans to cancelling, as today: the rest of a `Sequence` may need the robot, such as dialogue involving it, a sound it makes, or a script that uses it as a goal, and a `Sequence` is like a run of `await`s in C#, where one that throws stops the rest; .NET agrees, since a timeout cancels what awaits it. Claude's counter: a cancellation is never reported (`055 §1`), so a beat cut short by a removal stops silently, and a level whose progress hangs on it is softlocked with nothing in the log; going on makes the steps that needed the robot fail loudly, as actions on a removed entity, and lets the steps that only needed to come after it, such as a door closing, still run. In C#, an awaiter that expects a cancellation can catch it; wiring has no catch. A middle way: cancel, as Neil leans, and log a route's chain that a scope's ending cancels, as a warning, so that a beat cut short is never silent. Decision (Neil): the middle way. A cancellation propagates, as today, and a chain that a scope's ending cancels up to a task nothing awaits is logged as a warning. A level that must handle a removal in its wiring gets a construct of its own for it, when one needs it. How the warning is raised is for the implementation: Claude's sketch is that the scheduler reports such tasks at the end of the run, as it reports unhandled failures (`055 §1.3`), to a sink that the world sends to `GD.PushWarning`; a chain cancelled because the scheduler stopped is not reported, since dropping a world cuts everything short on purpose.
  - Found while building it (Claude, with Neil): a script that scopes itself on purpose, such as `Test_NBodySimulation` ending when its bodies are gone, would cut short its route and warn every time. Decision (Neil): `ITick.WhileInScope(body)` runs a body in a tick's scope, and finishes, rather than being cancelled, when that scope ends, so that what comes after it goes on. A scope's ending cancels with a `ScopeEndedException` naming the scope, so that `WhileInScope` catches only its own: an outer scope's ending, or the scheduler's stopping, still propagates. So a run's owner chooses: `Scoped` alone cancels what awaits it, and `WhileInScope` ends quietly. Built so (Claude): the scheduler reports each task that a scope's ending cancelled, and that nothing has awaited by the end of the run, to a second sink, which the world sends to `GD.PushWarning`. The name is provisional: `While` suggests a loop, which it isn't.
  - Superseded (Neil, at Claude's suggestion): `WhileInScope` is removed. The door's action, the other use of a scope, has a goal, to be closed, so a scope's ending there means the goal wasn't met, and must cancel. Most scripts are beats with goals too. Open-ended work that should end quietly, such as `Test_NBodySimulation`, is usually a controller's, and when a script does it, it waits one tick at a time, so `While`, which checks its condition between steps and finishes when it fails, does the job with no scope at all. So `While` ends cooperatively and quietly, and `Scoped` preemptively, with a cancellation and, if nothing hears of it, a warning. A scope's cancellation is still a `ScopeEndedException`, so that the scheduler can tell it from its stopping, but it names no scope, and scopes are combined conditions again. If a case turns up for open-ended work with long waits that must end quietly, `InScope` is the name.
- [x] 3.7 A side effect of scopes, under (a) or (c) of `054 §1.2`, or `054 §1.4`: cancelling everything without dropping the world, such as to start an important cutscene (`053 §4.2`), could run what it may interrupt on a scope of its own.
  - Noted (Neil): yes, and scoped ticks give several ways to set it up, when something needs it.
- [x] 3.8 A script about several entities (Neil's corner cases). One that keeps two entities near each other, by driving both, means nothing once either is gone, so it should end when either is removed. One that drives a conversation between two entities in callouts, outside a cutscene, should go on when the player kills one, and react. Neither fits a tick per entity: under (a) of `054 §1.2` a scope has one parent, under (b) a chain can't cross schedulers, and under (c) as first put, a scope is one entity's. Option (Claude): scopes belong to runs, not entities.
  - Each run gets a scope of its own, as its world's `Tick`, linked to the entities whose lifetime it shares: removing an entity stops every scope linked to it. Scopes stay flat, as in (c) of `054 §1.2`, and a link is to a lifetime, not to a place in the scene's tree.
  - The runner links a script's scope to its entity parameters (§2.3), so that it ends when any of them goes: the first case. A parameter that the script outlives would be marked, such as with an attribute, and left unlinked.
  - The second case links neither speaker. Each line is an action on its speaker's controller, which runs on the speaker's scope (§3.4), so removing a speaker ends that line's run, and the script, awaiting it, learns of it and reacts. That needs the awaiter to go on rather than be cancelled (§3.6), since catching the cancellation is against the root's conventions (`053 §1.4`) and couldn't tell the speaker's removal from the world's being dropped. The script then asks whether the speaker is still there.
  - A run is cancelled only while it waits on its own scope. One suspended on a task of another scope, such as a door's `Close`, unwinds only once that task settles: usually soon, but not if it never does.
  - Neil: scripts make their own scopes, not the runner. A script may later find entities by name, position or other criteria, so scoping it to the entities passed in could cancel it early; and one like the conversation, whose character yells when the other dies, runs on the world's scope and checks on its entities itself.
  - Settled by `054`: scopes belong to runs, as conditions a script makes from its world's `Tick`, not to entities. The first case scopes its run to both entities being live; the second runs unscoped, or scoped to the player, and checks on its speakers itself. Whether an awaiter goes on when what it awaits is cancelled was decided against in §3.6.

## 4. The test case

A script earns its place when there are beats to sequence, such as following until the player reaches a place, then flying elsewhere, then dropping. Claude: a hover controller for the block, and a script that sets its goal, with at least two beats, so that the test exercises the script side.

- [~] 4.2 The test case, changed (Neil): `Test_NBodySimulation`, given any number of entities, two blocks and a robot in the level, sets their gravity to 0 and pulls them together as planets, N-body. Claude, for §2.4: a script may drive a body that has no controller, and drives one that has a controller through the controller.
